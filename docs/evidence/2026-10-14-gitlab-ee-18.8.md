## Defects and observations

1. **Tool defect, fixed in `819a871`: the first commit of an empty repository.** After `project create`, the new project has no branch, and `repo file create README.md --branch main` (and a `repo commit create` of new files) was `E_NOT_FOUND` at the dry-run ("The project has no branch with that name"), while GitLab's first commit creates the branch it names. The preview now checks GitLab's `empty_repo` when the branch is missing: the create can apply, and the plan says the commit creates the branch. Updates, deletes and moves there, and a missing branch of a repository with commits, are refused as before. Covered by `TestRepoFirstCommitInEmptyRepository`; R01 below is the live run.
2. **Observation (tool, low, open): a bulk label add on an issue that already has the label** is planned as `add: [pilot]` and reported `applied` with verification passed (I09, issue #1). GitLab got the request and the state matches, but nothing changed; a `no_change` block, as `repo file update` has, would say so.
3. **Observation (upstream): GitLab's basic code search returns the same hit twice** (a file-name match and a content match of `ledger.py`, line 1); `search code` passes both through (S04).
4. **Notes for the brief.** The main package is `./cmd/gitlab-cli` (the root package only embeds the changelog), and a build in a git checkout reports Go's pseudo-version (`1.2.18-0.<time>-<commit>`) rather than `1.2.18-dev`; both are semantic versions and changed nothing here. GitLab 18.8 removes a top-level group only after its 30-day adjourned period (`permanently_remove` is for subgroups and projects), so the cleanup removed the project for good and left the empty group marked for deletion, renamed `pilot-live-deletion_scheduled-<id>`.

## How it ran

- **Isolation.** `USERPROFILE`, `HOME`, `APPDATA`, `LOCALAPPDATA` and `TEMP` pointed at a fresh folder in the run directory, and `GITLAB_CLI_STATE_DIR` at a folder inside it (settings, scope, journal, confirm key); all of it was deleted after the run. The only keyring entry was `gitlab-cli` / `profile:pilot-live`, written by `auth login` and removed by `auth logout`.
- **Writes went only to the sandbox**: group `pilot-live` (admin API) and project `pilot-live/sandbox` (the tool's own `project create`). The scope granted `change`, `configure`, `artifact` and `dangerous` on the targets `pilot-live` (subtree) and `profiles/pilot-live` (exact), with `outputs` limited to the run's artifacts folder, so no write could reach the seeded eval projects, which were only read.
- **CI data.** `.gitlab-ci.yml` (committed by the tool) has a `build` job that leaves `out/result.txt` as an artifact and a `flaky` job that fails, so pipelines fail with one failed job and one artifact.
- **Every write** ran as a dry-run and then a confirm with its token; dangerous commands carried `--dangerous` in both. Each confirmed write is followed by a read-back through the admin API (`read_back` in the JSON).
